# Объяснение кода

Применяй, когда просят разобраться в проекте, объяснить модуль или
ответить «как это работает».

## Сначала прочитай, потом говори

Отвечай по коду, а не по названиям файлов и не по общим представлениям
о том, как такое обычно устроено. Если чего-то не читал — так и скажи,
вместо догадки.

Порядок разведки:

1. точка входа: `package.json` / `main` / `bin`, скрипты запуска;
2. README и конфиги — заявленное устройство;
3. основной поток: от входа по вызовам вглубь;
4. границы: где сеть, диск, база, внешние вызовы;
5. тесты — они показывают ожидаемое поведение лучше документации.

## Как отвечать

- Начни с одного абзаца: что это за система и как в ней движутся данные.
  Потом детали.
- Двигайся по потоку исполнения, а не по алфавиту файлов.
- Ссылайся на `файл:строка` — читающий должен уметь проверить.
- Объясняй **почему** так сделано, если это видно из кода: какое
  ограничение или требование это решает.
- Отдельно назови неочевидное: неявные зависимости, глобальное
  состояние, обходные пути, места, где легко ошибиться.
- Схема из нескольких строк текста часто понятнее абзаца прозы.

## Соблюдай масштаб вопроса

Спросили про одну функцию — расскажи про функцию, а не про весь проект.
Спросили «как устроено» — дай карту, не пересказывай каждый файл.

## Чего не делать

- Не пересказывай код построчно — это не объяснение.
- Не вставляй в ответ длинные листинги; приводи короткий фрагмент,
  если он нужен для мысли.
- Не выдумывай архитектурные обоснования, которых нет в коде.
- Не предлагай улучшения, если просили объяснить. Заметил проблему —
  одна строка в конце.
