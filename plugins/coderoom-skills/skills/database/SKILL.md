# Базы данных

Данные живут дольше кода. Схема и миграции — там, где ошибки дороже всего.

## Схема

- Моделируй по смыслу данных: правильные типы (деньги — не float, а decimal/копейки; время — с таймзоной), NOT NULL по умолчанию, внешние ключи с явным поведением ON DELETE.
- Нормализуй, пока нет доказанной причины денормализовать. Уникальные ограничения и проверки — на уровне БД, а не только в коде: БД — последний рубеж целостности.
- Именование единообразное (как уже принято в проекте).

## Запросы и производительность

- Индексируй под реальные запросы: колонки в WHERE/JOIN/ORDER BY. Индекс ускоряет чтение, замедляет запись — не индексируй всё подряд.
- Избегай N+1: подгружай связанные данные пачкой (JOIN / IN / eager load), а не в цикле. Это самая частая причина тормозов.
- Не тяни `SELECT *` и лишние строки — только нужные колонки, пагинация по ключу (keyset), а не большие OFFSET. Смотри план запроса (EXPLAIN), если медленно.

## Транзакции и целостность

- Связанные изменения — в одной транзакции (всё или ничего). Держи транзакции короткими; не делай в них внешних вызовов.
- Гонки «прочитал-изменил-записал» — оптимистичная блокировка (версия/updated_at) или атомарный UPDATE в БД, а не в приложении.

## Миграции

- Изменения схемы — только версионированными миграциями, обратимыми где возможно. Никогда не правь прод-схему руками.
- Ломающие изменения делай в несколько шагов (expand/contract): добавь новое → перенеси данные → переключи код → удали старое. Так деплой без простоя и с возможностью отката.
- На больших таблицах бойся долгих блокировок (добавление NOT NULL/индекса) — делай безопасно для твоей СУБД.

## Практика

Используй способ доступа к БД, принятый в проекте (ORM/запросы/миграции). После изменений — прогони миграции и тесты на тестовой базе, не на боевой.
