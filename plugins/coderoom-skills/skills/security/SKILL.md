# Безопасность

Не доверяй ничему, что пришло извне. Проектируй так, чтобы ошибка была безопасной по умолчанию.

## Ввод и инъекции

- Валидируй и нормализуй любой внешний ввод по allowlist (что разрешено), а не blocklist. Отвергай неожиданное.
- SQL — только параметризованные запросы/подготовленные выражения, никогда конкатенация. То же для команд ОС (не собирай shell-строку из ввода), LDAP, NoSQL.
- Вывод экранируй по контексту: HTML/attr/JS/URL — против XSS. Не вставляй пользовательские данные в HTML как есть.
- Path traversal: не склеивай пути из ввода; проверяй, что итог внутри разрешённой папки. Тип/размер загружаемых файлов — по allowlist.

## Доступ и секреты

- AuthZ на каждом действии и на уровне объекта: проверяй, что именно ЭТОТ пользователь имеет право на ЭТОТ ресурс (иначе IDOR). Не полагайся на «скрытость» URL.
- Секреты (ключи, пароли, токены) — из окружения/секрет-стора, не в коде и не в логах. Пароли — хэш с солью (bcrypt/argon2), не шифрование и не MD5/SHA1.
- Токены/сессии: короткий срок, ротация, инвалидция при выходе. Cookie — HttpOnly, Secure, SameSite.

## Прочее

- Ошибки наружу — без стеков и внутренних деталей; внутрь — логируй, но без секретов и PII.
- Зависимости: не тащи лишнее; проверяй известные уязвимости; фиксируй версии. Не выполняй код из недоверенного источника.
- Rate limiting на дорогих/чувствительных эндпоинтах (логин, отправка). CSRF-защита для форм с состоянием.
- Криптографию не изобретай — используй проверенные библиотеки и режимы.

## Ревью

Смотри на границы доверия: где входят внешние данные и что с ними делают до валидации. Отмечай конкретный сценарий эксплуатации, а не общие слова.
