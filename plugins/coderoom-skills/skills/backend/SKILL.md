# Backend

Пиши серверный код так, будто его будут поддерживать и масштабировать. Сначала — контракт и данные, потом реализация.

## Контракт и границы

- Определи контракт до кода: вход, выход, коды ошибок, инварианты. Держи слои раздельно: транспорт (HTTP) → сервис (бизнес-логика) → доступ к данным. Бизнес-логика не должна знать про HTTP.
- REST: существительные для ресурсов, правильные методы и статусы (200/201/204/400/401/403/404/409/422/429/500). POST — создание, PUT/PATCH — обновление, DELETE — удаление. Для операций, не ложащихся в CRUD, заводи явный эндпоинт-действие.
- Версионируй публичный API (`/v1`). Ломающие изменения — новая версия, а не тихая замена.

## Валидация и ошибки

- Валидируй вход на границе (тип, диапазон, обязательность) и возвращай 400/422 с понятным телом: что не так и в каком поле. Никогда не доверяй клиенту.
- Ошибки — единый формат ответа (`{error: {message, code}}`). Различай ожидаемые (4xx, отдай пользователю) и неожиданные (5xx, залогируй со стеком, наружу — общий текст без утечки внутренностей).
- Не глотай исключения. Либо обработай осмысленно, либо дай подняться до общего обработчика.

## Надёжность

- Идемпотентность для операций, которые могут повториться (платежи, вебхуки): ключ идемпотентности либо естественный уникальный ключ.
- Внешние вызовы — таймаут + ретрай с бэкоффом только для повторяемых ошибок (5xx/сеть), не для 4xx. Предусмотри деградацию при недоступности зависимости.
- Долгие операции — в фон (очередь/воркер), а не в HTTP-запрос. Ответь 202 + способ узнать статус.
- Конкурентность: транзакции для связанных изменений; оптимистичная блокировка (версия строки) против гонок «прочитал-поменял-записал».

## Безопасность и наблюдаемость

- AuthN (кто) и AuthZ (что можно) — на каждом защищённом эндпоинте, проверка прав на уровне ресурса, а не только маршрута. Секреты — из окружения, не в коде.
- Логируй структурно с correlation-id сквозь запрос; не логируй секреты и PII. Полезные метрики: латентность, коды ответов, ошибки зависимостей.

## Практика

Найди, как в проекте уже сделаны роутинг, валидация, ошибки и доступ к БД, — повторяй этот стиль. После изменений прогони тесты/линтер. Не тащи новые зависимости, если задачу решают уже подключённые.
